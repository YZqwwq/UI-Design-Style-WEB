# 现状文档工作流

路径均相对 `.project-manager/document/`。开始前读取已有 `index.md`（若存在），确认任务范围，保留已有知识、讨论稿及用户内容。

## 浅层概览

1. 优先使用用户已说明的用途，阅读 README、根级配置、已有资料与少量主要入口。目录名只作为线索，不能直接当成功能划分。
2. 信息足以描述主要可见能力及其入口后停止。遇到需要继续追踪的实现细节，记为未核对，不自动深入调用链或下一个模块。
3. 建立或补充 `index.md` 与 `current/index.md`。索引记录此次浅读范围；概览列出能力、简短说明、依据和理解边界。尚未建立功能文档时链接代码或资料，不创建虚假的文档链接。
4. 现有资料不足以判断能力时如实说明，不强行补齐清单。到此结束，不自动执行完整整理或留下必须遍历全项目的阅读任务。

## 指定功能建档

1. 从用户指定的功能及已有资料确定边界。明显歧义会改变阅读范围时再询问；否则直接开展相关工作。
2. 围绕该功能阅读入口、必要实现和调用关系。关联依赖只读到足够解释该功能，不顺带为依赖另建完整文档。
3. 默认建立 `current/<功能>.md`；现有功能文档则增量更新。功能包含多个独立职责、确有多篇内容时才拆目录和 `catalog.md`，不映射整棵源码目录。
4. 解释实际功能边界、关键行为、实现入口及限制；按需要补充证据和不确定性，不逐文件复述代码，也不为了填章节编造内容。
5. 更新能力概览中的对应链接和根索引覆盖记录。功能范围之外的内容保持原状。

## 范围内完整整理

1. 只有用户明确要求完整整理时使用；“建立文档”默认采用浅层概览。
2. 浅读后列出本次覆盖的主要功能范围，明确外部系统、缺失源码等边界。范围清楚时继续；关键划分有歧义时询问，不要求用户逐篇审批。
3. 按功能分批执行指定功能建档。复杂或大项目也可以完整整理边界明确的子系统，不以项目大小直接判断能否整理。
4. 进度只记录已完成范围、当前未完成范围与待解决问题，便于中断后接手；不把读过局部说成整个项目已经对齐。
5. 只有约定范围实际覆盖后才称完成；不可核对的部分明确排除或标注。一次用户纠正不证明其他文档全部正确。

## 局部维护与用户纠正

1. 根据本次变更、用户纠正或相关实现入口，定位已有受影响的功能文档；无需遍历全文或重新建档。
2. 区分实现变化、原理解错误与未来意图。核对当前实现和资料，修改已失效结论，保留仍有效内容。
3. 功能边界变化时同步调整相关文档链接、概览和目录；不机械新增一篇相互矛盾的说明。
4. 若该功能尚未建档且用户仅要求开发，不主动创建详细功能文档；必要时修正已有能力概览中的对应事实。
5. 保留不受影响的覆盖记录，用最新交接说明替换旧的阅读过程；不能因本次更新一个功能而将全部文档标为已复核。

## 轻量索引示意

内容有需要才出现，不要求照抄空章节：

```markdown
# 项目文档

## 导航
- 当前能力：current/index.md
- 项目目标：已有目标文档的实际路径（存在时登记）

## 覆盖与边界
- 已浅读：README、主要配置与入口。
- 已深入核对：本次实际完成的功能（没有则明确未建详细文档）。
- 未确认：影响理解但尚未验证的事项。

## 最近维护
- 本次完成：具体阅读及修改范围。
- 后续：仅记录本任务尚未完成的工作；没有则说明等待用户指定范围。
```

`current/index.md` 使用简短概览或能力表即可。模块目录只导航，不承担进度日志；功能正文记录稳定知识，根索引记录维护覆盖情况。
