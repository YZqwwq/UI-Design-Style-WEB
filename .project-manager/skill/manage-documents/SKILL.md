# 管理项目文档

## 责任与阅读边界

文档位于 `.project-manager/document/`，由 Agent 按功能维护。目标表达用户意图，现状记录已核对事实，计划表达未来安排；不能互相代替。

- 首次接入只浅层阅读并建立初步能力概览，不自动逐层阅读全部源码、不展开完整功能文档。
- 用户要求指定功能文档时，只深入该功能及理解它必需的依赖；用户明确要求完整整理时，才按明确范围分批覆盖。
- 普通开发可为完成任务深入阅读实现，但不顺带扩大文档建设范围。已有相关文档随实际变更或用户纠正同步维护；明确的只读、讨论或不改文档要求优先。
- 新建覆盖范围由用户任务触发。只涉及一个功能的请求不授权遍历所有功能；一次调用本 skill 不等于要求完整建档。

## 选择工作方式

| 当前任务 | 处理方式 |
| --- | --- |
| 首次接入、建立项目文档，未要求完整整理 | 浅层概览 |
| 为某个功能建立或补全文档 | 指定功能建档 |
| 明确要求完整建立项目文档 | 范围内完整整理 |
| 修改实现、修复问题或纠正已有理解 | 局部维护已有相关文档 |

建立或维护现状文档前，读取 [现状文档工作流](references/current-state.md)，只执行匹配方式。理解项目时先看已有文档入口，再读取任务相关内容；不默认加载整套文档。

## 文档职责与位置

以下为默认位置，已有等价文档时沿用并登记真实路径，不另建重复来源。只创建当前任务确实需要的文件。

- `index.md`：文档导航、实际覆盖范围、尚未确认处和最近维护进度。阅读进度集中于此，保留累计覆盖概况和最近一次交接，不追加无限历史日志。
- `current/index.md`：初步能力概览和已建功能文档入口；区分浅层可见能力与已深入核对内容。
- `current/<功能>.md`：单一功能的实际知识；复杂到需要多篇时再拆为功能目录，用 `catalog.md` 仅列子功能入口。
- `goals.md`：用户已明确的目的、范围与成功标准；优先复用已有对话和资料，不强制重新索取用途说明。
- `roadmap.md`：用户已确定的阶段安排、交付物与完成标准；备选建议与已确定计划分开，文档阅读待办不放入这里。

本次能力重点是现状建档。目标和计划按已明确内容维护，不自动生成项目方向、排期或占位章节。现有讨论稿保留其讨论性质，不直接升级为已确认目标或实现事实。

## 事实与纠正

- 结论来自实际阅读；记录能帮助核查的关键代码入口或资料路径。按内容组织章节，不要求所有功能套同一模板。
- 没找到不等于不存在，代码存在不等于运行中已启用，写完不等于已验证。跨服务或运行配置未经检查时明确边界。
- 用户说明“现在实际如此”时核对现状；“希望以后如此”进入目标或计划，不能直接改写当前实现。
- 纠正时检查相关概览、功能文档与导航，修订受影响内容；不为纠正一处而重新扫描全项目。用户说明与实现证据不一致时记录具体差异，不猜测哪一方代表线上事实。
- 维护时可记录 Git 提交与工作区状态辅助定位，但必须同时说明实际核对范围；同一提交下未提交内容也可能变化，最新提交不能证明整套文档已同步。
- 用户对关键功能边界的意图不清且影响工作时再询问；已有明确范围不重复请求确认。

## 完成说明

说明本次新增或修订的文档、实际读取范围、仍未确认或未覆盖的部分。链接应可定位，不能把浅层概览或局部更新宣称为全项目完整建档。
